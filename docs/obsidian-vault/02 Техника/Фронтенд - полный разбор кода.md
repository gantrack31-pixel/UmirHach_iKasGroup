# Фронтенд: полный разбор кода

## Назначение

Frontend - браузерная часть онлайн-деканата. Пользователь выбирает тип документа, прикрепляет файл и отправляет запрос backend. Вопрос можно оставить пустым. В ответ интерфейс показывает распознанные поля, предварительную комплектность, текстовый ответ и распознанный OCR текст.

Фронтенд не выполняет OCR, не запускает языковую модель и не принимает решение о принятии документа. Это выполняет backend. Сейчас текст ответа строится на фронте по шаблону, используя классификацию из API.

## Технологии и вход

- React 18 строит интерфейс из компонентов.
- TypeScript описывает модели UI и API.
- Vite запускает dev сервер и собирает приложение.
- SCSS хранит стили по разделам.
- Тесты запускаются встроенным Node test runner.

src/main.tsx подключает стили и рендерит App в элемент #root. В src/App.tsx путь /help показывает справочник, остальные пути открывают проверку. React Router не используется.

## Страница проверки

src/pages/DocumentCheckerPage.tsx собирает HeroSection, workflow проверки и footer. Основной сценарий находится в features/document-check/components/DocumentCheckWorkflow.tsx.

| Компонент | Назначение |
| --- | --- |
| DocumentUploadPanel | Выбор типа, зона загрузки, выбранный файл и ошибка |
| ExtractedFieldsPanel | Поля из ответа backend |
| CheckResultPanel | Комплектность, текст ответа и источники |
| QuestionForm | Ввод вопроса и отправка |
| HelpPage | Статичная инструкция |

Компоненты загрузки лежат в components/upload/, строка поля - в components/fields/, а статус, ответ и источники - в components/result/. Workflow связывает состояние с презентационными компонентами; панели не вызывают API самостоятельно.

## Состояние формы

Модель состояния находится в features/document-check/types/documentCheck.ts. Она содержит выбранный файл, тип документа, вопрос, последний результат, признак обработки и ошибки.

Хук hooks/useDocumentCheck.ts связывает интерфейс с reducer и сервисом:

- addFile проверяет и принимает выбранный файл.
- removeFile удаляет файл и результат.
- setDocumentType и setQuestion обновляют ввод и очищают устаревший результат.
- runCheck валидирует форму, запускает запрос и сохраняет результат или ошибку.

model/validateDocument.ts проверяет формат JPEG, PNG или PDF по расширению и MIME, размер до 10 МиБ, наличие файла и типа документа, длину вопроса до 2000 символов. Пустой вопрос допустим. Backend независимо проверяет вход повторно.

model/documentCheckReducer.ts описывает переходы состояния. check/started очищает старый результат и включает обработку; check/succeeded сохраняет ответ; check/failed отображает ошибку. Изменение вопроса и типа сбрасывает предыдущий ответ.

Типы документов пока хранятся статически в data/documentTypes.ts: study_certificate, academic_leave_application и internship_certificate. useDocumentTypes читает список через интерфейс DocumentTypeCatalog.

## Проверка комплектности: что происходит при пустом вопросе

Пользователь выбирает тип, загружает файл и нажимает «Проверить комплектность».
Вводить вопрос не требуется. Если вопрос введён, кнопка называется «Задать вопрос».
Во время обработки кнопка показывает «Проверяем…» и отключена.

Путь данных:

```text
QuestionForm → useDocumentCheck → ApiDocumentCheckService → analyzeDocument
  → prompt: «Содержит ли документ все обязательные сведения?»
  → обычный обработчик вопросов backend → результат проверки
```

В services/api/analyzeDocument.ts константа COMPLETENESS_QUESTION задаёт точный
текст стандартного вопроса. Если input.question.trim() пуст, в multipart
отправляется эта константа. Если ввод непустой, передаётся исходный вопрос
вместе с пробелами по краям. Подстановка выполняется при отправке и не заполняет
поле формы.

Frontend всегда отправляет непустой prompt. Backend сохраняет исходный контракт
с обязательным вопросом; отдельная ветка обработки пустого вопроса не нужна.
Классификация, OCR и проверка выполняются существующим кодом backend.

Для ручной проверки загрузите data/documents/open-002.pdf как справку об обучении
и нажмите «Проверить комплектность» с пустым вводом. Должны появиться пропуск даты
выдачи и действие по нему. Во вкладке Network проверьте Form Data: prompt должен
содержать «Содержит ли документ все обязательные сведения?». Затем задайте свой
вопрос: он должен уйти без подмены.

Если сервер сообщает prompt: Field required, убедитесь, что браузер использует
актуальную версию frontend и отправляет prompt. В тестах проверяются пустая строка,
пробельный ввод, неизменность пользовательского вопроса и обязательность файла
с типом документа. Порядок остальных проверок формы сохраняется.

## Выбор сервиса и API

Интерфейс DocumentCheckService задаёт метод analyze. services/documentCheckService.ts выбирает API сервис по умолчанию или демо сервис, если VITE_USE_DEMO_SERVICE=true. Демо режим показывает фиксированные примеры и не обрабатывает загруженный файл.

Настройки Vite читаются в src/shared/config/env.ts. Для локального backend файл frontend/.env.local обычно содержит:

~~~dotenv
VITE_USE_DEMO_SERVICE=false
VITE_OCR_API_URL=/ocr-api
~~~

vite.config.ts проксирует /ocr-api к http://127.0.0.1:8000 и убирает этот префикс перед запросом. Это работает в dev сервере. Production серверу нужен собственный reverse proxy или прямой API URL с настроенным CORS.

services/ApiDocumentCheckService.ts координирует отправку, чтение JSON, проверку ответа и преобразование для UI. services/api/analyzeDocument.ts отправляет POST /analyze как multipart/form-data:

| Поле | Назначение |
| --- | --- |
| photos | Один файл |
| prompt | Обязательная строка: введённый вопрос или стандартный вопрос о комплектности |
| document_type | Код типа документа |

Content-Type не задаётся вручную: браузер добавляет multipart boundary. Ошибки FastAPI и сети преобразуются функцией services/api/readApiError.ts. Она обрабатывает, в частности, HTTP 413, 422, 503 и 504, а также строковый и массивный detail.

## Проверка контракта и mapping

Ответ сначала считается неизвестным JSON. services/api/parseAnalyzeResponse.ts проверяет допустимый тип документа, значения полей, статусы комплектности, массивы пропусков и источников, а также классификацию вопроса. Для классификации field проверяется, что указанное поле есть в fields. Если форма ответа неверна, UI показывает ошибку о несовпадении версий backend.

Контракт описан в features/document-check/types/api.ts. Backend возвращает:

- document_type;
- fields со строками или boolean;
- необязательный ocr_text;
- validation со статусом document_ok или missing_fields, списком пропусков и источников;
- classification с intent field, validation, decision или unsupported.

services/api/mapAnalyzeResponse.ts преобразует API DTO в модель DocumentCheckResult для интерфейса. Здесь создаются подписи и значения полей, статусы, сводка комплектности, ссылки на источники и текст OCR. Подписи находятся в data/fieldLabels.ts. Если ocr_text отсутствует, показывается текст-заглушка; остальные данные продолжают отображаться.

## Формирование ответа

model/buildDocumentAnswer.ts использует classification backend и выбирает шаблон:

- field показывает запрошенное значение или сообщает, что оно не найдено;
- boolean false для подписи или печати означает известное отсутствие;
- validation показывает пропущенные обязательные поля и напоминает о решении сотрудника деканата;
- decision объясняет, кто принимает окончательное решение;
- unsupported сообщает, что ответа нет.

Ответ на вопрос и комплектность независимы. Например, отсутствие подписи может быть известным ответом и одновременно обязательным пропуском. Статус берётся из validation, а текст ответа - из classification. Положительный статус не означает, что документ принят.

Фронтенд не читает Положение и не генерирует произвольные ответы. Когда backend начнёт возвращать готовый ответ, обновляются типы API, проверка структуры и mapper. Компоненты лучше продолжать снабжать моделью DocumentCheckResult.

## Список действий: как он устроен

Под результатом проверки теперь есть блок «Что сделать перед подачей».
Он появляется, если backend вернул обязательные пропуски. Для полного документа
список пуст и не занимает место. Рекомендации отображаются независимо от того,
спрашивал студент о комплектности или о конкретном поле.

Данные проходят через следующие файлы:

| Этап | Файл внутри frontend/src/features/document-check/ |
| --- | --- |
| Получить пропуски и источники backend | services/api/mapAnalyzeResponse.ts |
| Превратить их в рекомендации | model/buildDocumentActions.ts |
| Описать элемент DocumentNextAction | types/documentCheck.ts |
| Разместить список под результатом | components/result/CheckAnswer.tsx |
| Показать строки и раскрываемый текст | components/result/DocumentActions.tsx |

buildDocumentActions получает document_type и validation. Он не распознаёт
документ и не пересчитывает правила: на каждый уникальный ключ missing_fields
создаёт fieldId, title, description и sources. Русское название берёт из
getFieldLabel. Готовые действия mapper сохраняет в result.validation.actions.
Это свойство интерфейса; backend его не возвращает.

Действия предлагают сверить оригинал. Если поле или отметка есть, нужно
загрузить более чёткое изображение. Если их нет — заполнить заявление либо
обратиться в выдавший справку вуз или организацию. Рекомендации учитывают,
кто должен подписать документ: студент, сотрудник вуза или руководитель практики.
Для заявления печать не требуется.

Текстовым полям соответствуют пункты 3.1, 4.1 или 5.1; подписи — 3.2, 4.2 или
5.2; печати справок — 3.3 или 5.3. Ссылка добавляется только если требование
есть в validation.sources. Правила и тексты согласовываются вручную с Положением.

### Почему блок компактный

Каждая строка содержит название замечания, ссылку на требование и знак «+».
Нажатие раскрывает рекомендацию через обычные HTML details/summary; сервер
при этом не вызывается. В открытой строке знак меняется на «−».

Оформление находится в frontend/src/styles/_results.scss. Классы
.document-actions и .document-action-list задают небольшие отступы и высоту
списка до 230 px. При переполнении прокручивается список, а не растёт весь блок.

### Где менять и как проверить

Тексты меняйте в model/buildDocumentActions.ts, структуру строк — в
components/result/DocumentActions.tsx, размеры и отступы — в _results.scss.
Не изменяйте HTTP-клиент для правки текста рекомендации: запрос API прежний.

Для ручной проверки загрузите data/documents/open-002.pdf, выберите справку
об обучении и задайте вопрос о комплектности. Должна появиться строка «Дата
выдачи» со ссылкой на 3.1. Раскройте её и проверьте текст. На полном документе
блок не должен появляться; при большом количестве замечаний проверьте прокрутку.

Тесты api-document-check.test.mjs подставляют ответы backend и проверяют
рекомендации для трёх типов, источники и пустой список для полного документа.
Они не проверяют внешний вид в браузере. Демо-примеры без validation действий
не содержат.

## Справка и общие части

src/pages/HelpPage.tsx собирает статическую справку из features/help/: заголовок, пример документа, шаги и советы. Тексты и пути к иллюстрациям находятся в features/help/data/. Backend справка не вызывает.

В src/shared/ находятся общие HeroSection, SiteFooter, Icon, PanelHeading, чтение переменных окружения и утилита форматирования размера файла.

## Стили

src/styles.scss подключает SCSS разделы:

- _base.scss - переменные, типографика и общие элементы;
- _layout.scss - сетка страницы и панели;
- _hero.scss - верхний блок;
- _upload.scss - загрузка файла;

При изменении JSX сохраняйте существующие классы или обновляйте соответствующие SCSS правила. Адаптивность в основном описана в _responsive.scss.

## Тестирование и запуск

Команды выполняются из frontend/:

~~~bash
npm ci
npm test
npm run build
npm run dev
~~~

npm test запускает tests/*.test.mjs встроенным Node test runner. api-document-check.test.mjs проверяет API запрос, разбор ответа, классификации и ошибки. document-check-state.test.mjs проверяет ограничения и переходы состояния формы.

npm run build запускает tsc --noEmit и затем собирает сайт в dist/. Для настоящего OCR backend должен работать на 127.0.0.1:8000. Тесты frontend не запускают OCR или языковую модель и не измеряют качество распознавания.
