## 1. Что такое frontend в этом проекте

Frontend находится в папке:

```text
Code/frontend/
```

Это пользовательский интерфейс проекта «Онлайн-деканат». Сейчас он реализует один основной экран:

1. Пользователь выбирает тип документа.
2. Пользователь загружает файл.
3. Пользователь пишет вопрос.
4. Интерфейс запускает демонстрационную проверку.
5. На экране появляются найденные поля и пример ответа.

Важно: текущая frontend-часть пока не делает настоящую OCR-проверку. Файл выбирается в браузере, проходит локальную валидацию по типу и размеру, но его содержимое не распознаётся. Результат берётся из заранее подготовленных demo-сценариев.

Это сделано специально: интерфейс уже показывает будущий пользовательский поток, а backend и OCR можно подключить позже через сервисный контракт.

## 2. Технологии frontend-части

Фактический frontend-стек по коду:

| Технология | Где видно | Зачем нужна |
|---|---|---|
| React 18 | `package.json`, `src/main.tsx`, компоненты `.tsx` | Компонентная модель интерфейса |
| React DOM | `src/main.tsx` | Монтирование React-приложения в DOM |
| TypeScript | `tsconfig.json`, файлы `.ts` и `.tsx` | Строгая типизация состояния, props, сервисов и результатов |
| Vite | `vite.config.ts`, `package.json` | Dev server, сборка и быстрый frontend workflow |
| SCSS / Sass | `styles.scss`, `src/styles/*.scss`, зависимость `sass` | Разбиение стилей на модули и использование Sass-сборки |
| HTML | `index.html` | Базовый документ, корневой DOM-узел и favicon |
| CSS custom properties | `_base.scss` | Цвета и дизайн-токены через переменные `--ink`, `--teal`, `--muted` |
| Browser File API | `DocumentUploadPanel`, `useDocumentCheck` | Получение выбранного пользователем файла |
| React hooks | `useReducer`, `useState`, `useRef`, `useEffect` | Управление состоянием, drag-and-drop, загрузка справочников |

Отдельный важный момент: в заметке [[02 Техника/Технологический стек]] написано `React + Vite + TypeScript + Tailwind`, но в реальном frontend-коде Tailwind не используется. Стили написаны на SCSS. Если команда решила отказаться от Tailwind, заметку про стек стоит обновить. Если Tailwind всё ещё планируется, нужно отдельно добавить его конфигурацию и перевести стили.

Папка `src/` построена по понятной схеме:

- `pages/` содержит страницы приложения.
- `features/` содержит предметные модули, сейчас только `document-check`.
- `shared/` содержит переиспользуемые компоненты и утилиты.
- `styles/` содержит SCSS-модули для внешнего вида.
- `main.tsx` запускает приложение.
- `App.tsx` выбирает, какую страницу показать.

Это хорошая структура для роста проекта, потому что логика проверки документа уже отделена от общих компонентов и от страницы.

## 4. Папка assets

Папка:

```text
Code/frontend/assets/
```

Содержит статические визуальные ресурсы frontend-части.

Сейчас там есть:

```text
assets/
  .DS_Store
  pictures/
    image.png
    Знак — шапочка, диплом и печать.svg
```

### `assets/pictures/image.png`

Файл:

```text
Code/frontend/assets/pictures/image.png
```

Это PNG-картинка размером `1672 x 941`, RGBA. Она используется в hero-блоке как большая фоновая иллюстрация:

```tsx
<img className="hero-art" src="/assets/pictures/image.png" alt="" />
```

Так как путь начинается с `/assets/...`, Vite отдаёт картинку как статический файл из корня frontend-проекта при dev server. В интерфейсе это декоративное изображение, поэтому `alt=""`. Пустой alt правильный для декоративных изображений: скринридер не будет читать бесполезное описание.

### `assets/pictures/Знак — шапочка, диплом и печать.svg`

Файл:

```text
Code/frontend/assets/pictures/Знак — шапочка, диплом и печать.svg
```

Это SVG-логотип/знак проекта: академическая шапочка, диплом и печать. Он используется в `HeroSection` внутри ссылки бренда:

```tsx
<img src="/assets/pictures/Знак%20%E2%80%94%20шапочка,%20диплом%20и%20печать.svg" alt="" />
```

Имя файла содержит пробелы, кириллицу, запятую и длинное тире. Поэтому в коде путь URL-encoded: пробелы заменены на `%20`, длинное тире на `%E2%80%94`.

Для разработки это работает, но для команды может быть удобнее переименовать файл во что-то вроде:

```text
dekanat-logo.svg
```

Так меньше риск ошибиться в путях, особенно при переносе на production-сервер.

### `assets/.DS_Store`

Файл:

```text
Code/frontend/assets/.DS_Store
```

Это системный файл macOS. Он не нужен приложению. Обычно такие файлы добавляют в `.gitignore`, чтобы они не попадали в репозиторий.

## 5. Точка входа index.html

Файл:

```text
Code/frontend/index.html
```

Это базовый HTML-документ приложения. В нём есть:

```html
<div id="root"></div>
```

Именно в этот элемент React монтирует всё приложение.

Также в `index.html` подключается frontend-точка входа:

```html
<script type="module" src="/src/main.tsx"></script>
```

Vite понимает этот импорт, обрабатывает TypeScript/React, собирает зависимости и запускает приложение.

Что ещё важно:

- `lang="ru"` показывает, что интерфейс русскоязычный.
- `meta viewport` нужен для адаптивности на мобильных устройствах.
- `theme-color="#f7fbfd"` задаёт цвет темы браузера.
- favicon задан inline через SVG data URL.
- `<title>Онлайн-деканат</title>` задаёт заголовок вкладки.

## 6. Точка входа React main.tsx

Файл:

```text
Code/frontend/src/main.tsx
```

Код:

```tsx
import React from "react";
import ReactDOM from "react-dom/client";
import App from "./App";
import "./styles.scss";

ReactDOM.createRoot(document.getElementById("root")!).render(
  <React.StrictMode>
    <App />
  </React.StrictMode>,
);
```

Что здесь происходит:

1. Импортируется React.
2. Импортируется `ReactDOM` из современного API `react-dom/client`.
3. Импортируется корневой компонент `App`.
4. Импортируются глобальные стили `styles.scss`.
5. React ищет DOM-элемент `#root`.
6. Внутрь `#root` рендерится приложение.
7. Приложение обёрнуто в `React.StrictMode`.

`React.StrictMode` нужен в разработке: он помогает находить потенциальные проблемы. Например, некоторые эффекты могут вызываться повторно в dev-режиме, чтобы обнаружить небезопасную логику.

Оператор `!` после `getElementById("root")` говорит TypeScript: «мы уверены, что элемент существует». Это допустимо, потому что `index.html` действительно содержит `<div id="root"></div>`.

## 8. Страница DocumentCheckerPage.tsx

Файл:

```text
Code/frontend/src/pages/DocumentCheckerPage.tsx
```

Это главный экран frontend-приложения.

Он собирает вместе:

- hero-блок;
- панель загрузки документа;
- панель найденных полей;
- панель результата;
- форму вопроса;
- footer.

Ключевые импорты:

```tsx
import {
  CheckResultPanel,
  DocumentUploadPanel,
  ExtractedFieldsPanel,
  QuestionForm,
  useDocumentCheck,
  useDocumentTypes,
} from "../features/document-check";
import {
  documentCheckService,
  documentTypeCatalog,
} from "../features/document-check/services/documentCheckService";
import { HeroSection, SiteFooter } from "../shared";
```

Здесь видно важное архитектурное решение:

- страница не знает деталей reducer;
- страница не знает demo-сценариев;
- страница не сама валидирует файл;
- страница только соединяет фичу, сервисы и UI-компоненты.

Внутри компонента:

```tsx
const documentCheck = useDocumentCheck(documentCheckService);
const documentTypes = useDocumentTypes(documentTypeCatalog);
```

`useDocumentCheck` управляет всем состоянием проверки.

`useDocumentTypes` загружает список типов документов.

Дальше `DocumentCheckerPage` прокидывает данные и обработчики в компоненты:

- `DocumentUploadPanel` получает файл, ошибки, тип документа, список типов и callbacks.
- `ExtractedFieldsPanel` получает поля результата.
- `CheckResultPanel` получает статус, признак обработки, текущий шаг и результат.
- `QuestionForm` получает вопрос, ошибку и обработчики изменения/submit.

Такой подход делает страницу «контейнером»: она связывает части, но не содержит лишней бизнес-логики.

## 9. Feature-модуль document-check

Папка:

```text
Code/frontend/src/features/document-check/
```

Это главный предметный модуль frontend-приложения. Он отвечает за сценарий «проверить документ».

Внутри него код разделён так:

```text
document-check/
  README.md
  index.ts
  components/
  data/
  hooks/
  model/
  services/
  types/
```

### `README.md`

В README фичи уже описана основная идея:

- `components/` рисуют интерфейс и не вызывают API напрямую;
- `model/` содержит reducer, начальное состояние и чистую валидацию;
- `types/` описывает модель результата и границы сервисов;
- `data/` содержит demo-сценарии, тексты статусов и статический каталог типов;
- `services/` содержит текущую локальную реализацию;
- `hooks/` связывает состояние с сервисами.

Это важный файл для новых разработчиков. Он кратко объясняет, как заменить demo на backend.

### Почему это хорошее разделение

Компоненты не импортируют `demoScenarios` и не знают, откуда пришёл результат. Они получают props.

Сервис не знает, как выглядит страница. Он получает input и возвращает result.

Reducer не знает про API. Он только меняет состояние по action.

Такой код проще тестировать и проще подключать к настоящему backend.

## 11. Типы данных documentCheck.ts

Файл:

```text
Code/frontend/src/features/document-check/types/documentCheck.ts
```

Это центральная типовая модель фичи.

### CheckStatus

```ts
export type CheckStatus = "success" | "warning" | "unknown";
```

Статус результата проверки:

- `success` - документ условно соответствует требованиям;
- `warning` - есть замечания;
- `unknown` - данных недостаточно.

### DocumentType

```ts
export type DocumentType =
  | "study_certificate"
  | "application"
  | "internship_certificate"
  | "other";
```

Тип документа, выбранный пользователем:

- справка об обучении;
- заявление;
- справка о практике;
- другой документ.

### FieldStatus

```ts
export type FieldStatus = "found" | "review" | "missing";
```

Статус отдельного найденного поля:

- `found` - поле найдено;
- `review` - поле требует ручной проверки;
- `missing` - поле не найдено.

### UploadedDocument

```ts
export type UploadedDocument = {
  file: File;
  name: string;
  size: number;
  mimeType: string;
};
```

Это обёртка над браузерным `File`. Она хранит:

- сам объект `File`;
- имя файла;
- размер;
- MIME type.

Зачем хранить не только `File`: UI часто нужно показывать имя и размер, а сервису нужен сам `File` для будущей отправки на backend.

### ExtractedField

```ts
export type ExtractedField = {
  label: string;
  value: string;
  status: FieldStatus;
};
```

Модель поля, которое показывается в панели «Что найдено».

Примеры:

- ФИО;
- Вуз;
- Дата выдачи;
- Подпись;
- Печать.

### StatusContent

```ts
export type StatusContent = {
  label: string;
  title: string;
  answer: string;
  icon: string;
};
```

Описание статуса для UI:

- короткая label;
- заголовок;
- текст ответа по умолчанию;
- icon как строка.

### DocumentCheckResult

```ts
export type DocumentCheckResult = {
  status: CheckStatus;
  fields: ExtractedField[];
  answer: string;
  sourceTitle: string;
  sourceReference: string;
  sourceExcerpt: string;
};
```

Это результат проверки, который UI умеет показать.

Он содержит:

- итоговый статус;
- список найденных полей;
- ответ пользователю;
- название источника;
- ссылку/описание источника;
- выдержку из источника.

Сейчас источники демонстрационные. В будущем сюда нужно передавать реальные ссылки на правило, пункт положения или evidence.

### DocumentCheckInput

```ts
export type DocumentCheckInput = {
  file: File;
  documentType: DocumentType;
  question: string;
};
```

Это входные данные для сервиса проверки:

- файл;
- тип документа;
- вопрос пользователя.

### DocumentCheckState

```ts
export type DocumentCheckState = {
  file: UploadedDocument | null;
  documentType: DocumentType | "";
  question: string;
  result: DocumentCheckResult | null;
  isProcessing: boolean;
  processingStep: string;
  uploadError: string;
  formError: string;
  documentTypeError: string;
};
```

Это полное состояние формы проверки.

Почему `documentType` может быть пустой строкой: пользователь сначала ещё ничего не выбрал, а select должен иметь пустое значение.

Почему ошибок несколько:

- `uploadError` относится к файлу;
- `documentTypeError` относится к select типа документа;
- `formError` относится к вопросу или общей ошибке проверки.

Так UI может показывать ошибки рядом с нужным полем.

### DocumentCheckAction

## 14. Reducer documentCheckReducer.ts

Файл:

```text
Code/frontend/src/features/document-check/model/documentCheckReducer.ts
```

Reducer - это функция, которая получает текущее состояние и action, а возвращает новое состояние.

Сигнатура:

```ts
export function documentCheckReducer(
  state: DocumentCheckState,
  action: DocumentCheckAction,
): DocumentCheckState
```

### `file/accepted`

Когда файл прошёл валидацию:

- записывает файл в state;
- очищает старый result;
- очищает ошибки.

Это логично: новый файл значит старый результат больше не актуален.

### `file/removed`

Когда пользователь удаляет файл:

- `file` становится `null`;
- `result` очищается;
- ошибки очищаются.

### `file/rejected`

Когда файл не прошёл валидацию:

- записывается `uploadError`.

Например: «Поддерживаются только файлы PDF, JPG и PNG».

### `documentType/changed`

Когда пользователь меняет тип документа:

- обновляется `documentType`;
- очищается старый result;
- очищаются ошибки типа документа и формы.

Это тоже важно: если результат был для справки, а пользователь переключился на заявление, старый результат нельзя показывать как актуальный.

### `question/changed`

Когда пользователь меняет вопрос:

- обновляется `question`;
- очищается старый result;
- очищается ошибка формы.

### `validation/failed`

Когда перед запуском проверки не хватает данных:

- если проблема в файле, ошибка идёт в `uploadError`;
- если проблема в типе документа, ошибка идёт в `documentTypeError`;
- если проблема в вопросе, ошибка идёт в `formError`.

Reducer получает `target` и сам раскладывает сообщение по нужному полю.

### `check/started`

Когда проверка началась:

- `isProcessing: true`;
- `result: null`;
- `processingStep: "Подготавливаем проверку…"`;
- все ошибки очищаются.

### `check/stepChanged`

Когда сервис сообщает новый шаг:

- обновляется `processingStep`.

Это позволяет показывать пользователю, что процесс движется.

### `check/succeeded`

Когда сервис успешно вернул результат:

- `isProcessing: false`;
- `processingStep: ""`;
- `result` записывается в state.

### `check/failed`

Когда сервис упал:

- `isProcessing: false`;
- `processingStep: ""`;
- сообщение ошибки записывается в `formError`.

### Проверка exhaustiveness

В `default` есть строка:

```ts
action satisfies never;
```

Это TypeScript-приём. Он помогает заметить, если в тип `DocumentCheckAction` добавили новый action, но забыли обработать его в reducer.

## 16. Хук useDocumentCheck

Файл:

```text
Code/frontend/src/features/document-check/hooks/useDocumentCheck.ts
```

Это главный хук сценария проверки документа.

Он:

- создаёт reducer;
- принимает сервис проверки;
- валидирует файл;
- запускает проверку;
- отдаёт компонентам состояние и callbacks.

### Создание состояния

```ts
const [state, dispatch] = useReducer(
  documentCheckReducer,
  initialDocumentCheckState,
);
```

Состояние управляется reducer-ом, а не множеством отдельных `useState`. Это хорошо, потому что форма имеет много связанных полей и переходов.

### addFile

```ts
const addFile = (file?: File) => {
  if (!file) return;
  const error = validateUploadedFile(file);
  if (error) {
    dispatch({ type: "file/rejected", message: error });
    return;
  }
  dispatch({
    type: "file/accepted",
    file: { file, name: file.name, size: file.size, mimeType: file.type },
  });
};
```

Что делает:

1. Если файла нет, ничего не делает.
2. Проверяет файл через `validateUploadedFile`.
3. Если есть ошибка, отправляет `file/rejected`.
4. Если всё хорошо, создаёт `UploadedDocument` и отправляет `file/accepted`.

### runCheck

```ts
const runCheck = async () => {
  const validationError = validateDocumentCheckInput(
    state.file?.file ?? null,
    state.documentType,
    state.question,
  );
  ...
};
```

Это обработчик запуска проверки.

Алгоритм:

1. Проверить, что есть файл, тип документа и вопрос.
2. Если ошибка есть, отправить `validation/failed`.
3. Собрать `input`.
4. Отправить `check/started`.
5. Вызвать `service.analyze`.
6. Во время выполнения принимать progress-сообщения.
7. При успехе отправить `check/succeeded`.
8. При ошибке отправить `check/failed`.

### Статус

Хук возвращает:

```ts
status: state.result?.status ?? (state.isProcessing ? "unknown" : null)
```

Это значит:

- если есть результат, берём статус из результата;
- если идёт обработка, временно показываем `unknown`;
- если нет результата и не идёт обработка, статус `null`.

### Что возвращает хук

Хук возвращает всё состояние плюс методы:

- `addFile`;
- `removeFile`;
- `setQuestion`;
- `setDocumentType`;
- `runCheck`.

Компоненты не используют `dispatch` напрямую. Они вызывают понятные методы.


### Получение контента статуса

```ts

```

Если статуса нет, будет empty state.

### Список статусов

Если `status` есть, показывается блок из трёх статусов:

- соответствует требованиям;
- есть замечания;
- недостаточно данных.

Основная карточка результата имеет класс:

```tsx

```

То есть CSS знает:

- есть ли статус;
- какой именно статус;
- идёт ли обработка.

### Processing state

Если `isProcessing`, показывается:

- spinner;
- текущий progress step;
- пояснение, что OCR не запускается.

Текущий шаг приходит из `processingStep`, который обновляет сервис через `onProgress`.

Если обработки нет и статуса нет:

```text
Результат появится здесь

```

Если статус есть, компонент показывает:

- заголовок;
- иконку;
- текст ответа;
- раскрываемый блок источника через `<details>`.

Для текста ответа используется:

```tsx
result?.answer ?? currentStatus.answer
```

То есть если в результате есть конкретный ответ, показывается он. Если результата почему-то нет, используется fallback из `statusContent`.

### Источник

Источник оформлен через `<details>` и `<summary>`.

Это хороший HTML-паттерн:

- работает без JavaScript;
- доступен с клавиатуры;
- имеет понятную семантику.

Внутри показывается `sourceExcerpt`.

В будущем сюда можно выводить:

- пункт положения;
- rule_id;
- evidence;
- ссылку на страницу документа;
- confidence OCR.

## 31. Утилита formatSize

Файл:

```text
Code/frontend/src/shared/utils/formatSize.ts
```

Функция:

```ts
export function formatSize(size: number) {
  return size >= 1024 * 1024
    ? `${(size / (1024 * 1024)).toFixed(1)} МБ`
    : `${Math.max(1, Math.round(size / 1024))} КБ`;
}
```

Она форматирует размер файла для UI:

- если размер от 1 МБ, показывает МБ с одним знаком после запятой;
- иначе показывает КБ;
- минимум показывает `1 КБ`, даже если файл меньше килобайта.

Примеры:

| Вход | Вывод |
|---:|---|
| `500` | `1 КБ` |
| `1536` | `2 КБ` |
| `1048576` | `1.0 МБ` |
| `1572864` | `1.5 МБ` |

## 37. Как сейчас работает пользовательский сценарий

Полный поток:

```text
Пользователь открывает страницу
  -> main.tsx монтирует App
  -> App рендерит DocumentCheckerPage
  -> DocumentCheckerPage создаёт useDocumentCheck и useDocumentTypes
  -> useDocumentTypes получает список типов документов
  -> пользователь выбирает тип документа
  -> DocumentUploadPanel вызывает onDocumentTypeChange
  -> useDocumentCheck dispatch(documentType/changed)
  -> пользователь выбирает или перетаскивает файл
  -> DocumentUploadPanel вызывает onFileAdd(file)
  -> useDocumentCheck валидирует файл
  -> reducer сохраняет UploadedDocument
  -> пользователь вводит вопрос
  -> QuestionForm вызывает onQuestionChange
  -> reducer сохраняет question
  -> пользователь нажимает Проверить
  -> QuestionForm вызывает onSubmit
  -> useDocumentCheck.runCheck валидирует input
  -> dispatch(check/started)
  -> DemoDocumentCheckService.analyze имитирует обработку
  -> onProgress обновляет processingStep
  -> service возвращает demoScenarios[documentType]
  -> dispatch(check/succeeded)
  -> ExtractedFieldsPanel показывает fields
  -> CheckResultPanel показывает статус, ответ и источник
```

Если файл плохой:

```text
onFileAdd
  -> validateUploadedFile
  -> ошибка
  -> dispatch(file/rejected)
  -> uploadError появляется в DocumentUploadPanel
```

Если пользователь нажал «Проверить» без данных:

```text
runCheck
  -> validateDocumentCheckInput
  -> validation/failed
  -> ошибка появляется рядом с файлом, типом документа или вопросом
```

Если сервис упадёт:

```text
service.analyze throws
  -> catch
  -> check/failed
  -> formError: "Не удалось сформировать результат. Попробуйте ещё раз."
```

## 39. Как подключать настоящий backend

Подключение backend лучше делать через новую реализацию `DocumentCheckService`, а не через переписывание компонентов.

### Шаг 1. Согласовать API-контракт

Сначала нужно свериться с:

- [[02 Техника/Контракт API]]
- backend-схемами;
- форматом `results.json`;
- требованиями организаторов.

Нужно понять:

- endpoint;
- HTTP method;
- формат upload;
- названия полей;
- формат результата;
- формат ошибок;
- нужен ли progress.

### Шаг 2. Создать ApiDocumentCheckService

Например:

```text
src/features/document-check/services/ApiDocumentCheckService.ts
```

Он должен реализовать:

```ts
DocumentCheckService
```

То есть иметь метод:

```ts
analyze(input, onProgress): Promise<DocumentCheckResult>
```

Внутри:

1. Создать `FormData`.
2. Добавить файл.
3. Добавить `documentType`.
4. Добавить `question`.
5. Отправить `fetch`.
6. Проверить HTTP status.
7. Преобразовать backend DTO в `DocumentCheckResult`.
8. Вернуть результат.

### Шаг 3. Не пускать DTO в UI

Если backend вернёт поля в другом формате, например:

```json
{
  "overall_status": "ok",
  "extracted_fields": [],
  "evidence": []
}
```

Не нужно заставлять компоненты знать эти названия. Лучше сделать mapper:

```ts
function mapApiResultToDocumentCheckResult(dto): DocumentCheckResult
```

Так UI останется стабильным.

### Шаг 4. Заменить сервис

В файле:

```text
src/features/document-check/services/documentCheckService.ts
```

Заменить:

```ts
export const documentCheckService = new DemoDocumentCheckService();
```

На:

```ts
export const documentCheckService = new ApiDocumentCheckService();
```

### Шаг 5. Подумать про progress

Сейчас `onProgress` синхронно вызывается demo-сервисом.

Для backend есть варианты:

- оставить простой текст «Отправляем документ…», «Получаем результат…»;
- добавить polling по job id;
- использовать Server-Sent Events;
- использовать WebSocket.

Для hackathon-прототипа достаточно простого состояния без настоящего live progress.

### Шаг 6. Обработать ошибки

Нужно различать:

- файл слишком большой;
- backend недоступен;
- OCR не смог распознать документ;
- документ не поддерживается;
- ошибка валидации;
- внутренняя ошибка сервера.

Сейчас все ошибки сервиса превращаются в одно сообщение:

```text
Не удалось сформировать результат. Попробуйте ещё раз.
```

Для production лучше возвращать более точные сообщения.

## 40. Важные архитектурные решения

### Компоненты отделены от бизнес-логики

Компоненты получают props и callbacks. Они не знают, откуда данные.

Плюсы:

- проще тестировать;
- проще менять backend;
- меньше связности;
- компоненты можно переиспользовать.

### Reducer управляет сложным состоянием

Форма проверки имеет много связанных состояний:

- файл;
- тип;
- вопрос;
- ошибки;
- progress;
- result.

Reducer помогает не разнести эту логику по множеству `useState`.

### Сервис внедряется в хук

`useDocumentCheck(service)` принимает сервис параметром. Это dependency injection.

Плюсы:

- можно подменить demo на API;
- можно написать mock service для тестов;
- хук не импортирует конкретный сервис.

### Типы задают границы системы

`DocumentCheckInput`, `DocumentCheckResult`, `DocumentCheckService` и `DocumentTypeCatalog` описывают, как части общаются друг с другом.

Это особенно важно перед подключением backend.

### Стили разделены по областям

SCSS-файлы не смешаны в один огромный файл. Есть отдельные области:

- base;
- layout;
- hero;
- upload;
- fields;
- results;
- question-footer;
- responsive.

## 41. Возможные проблемы и улучшения

### 1. Tailwind указан в документации, но не используется в коде

В [[02 Техника/Технологический стек]] указан Tailwind. В реальном коде нет Tailwind config и зависимостей Tailwind.

Нужно решить:

- обновить документацию на SCSS;
- или действительно добавить Tailwind.

### 2. Год в footer

`SiteFooter` пишет:

```text
Демо-версия · 2025
```

Но sprint-документация указывает 2026 год. Нужно проверить актуальность.

### 3. `.DS_Store` в assets

`assets/.DS_Store` не нужен приложению. Лучше добавить `.DS_Store` в `.gitignore` и убрать файл из репозитория, если он уже закоммичен.

### 4. Имя SVG-файла сложное

Файл:

```text
Знак — шапочка, диплом и печать.svg
```

Работает, но может создавать проблемы в URL, Docker, shell-командах и CI. Лучше переименовать в ASCII-имя.

### 5. `useDocumentTypes` возвращает loading/error, но страница их не использует

Сейчас:

```ts
const documentTypes = useDocumentTypes(documentTypeCatalog);
```

Но `isLoading` и `error` не отображаются.

Можно улучшить:

- disabled select, пока список грузится;
- текст ошибки, если каталог не загрузился.

### 6. Нет unit-тестов frontend

Сейчас нет тестов для:

- `validateUploadedFile`;
- `validateDocumentCheckInput`;
- `documentCheckReducer`;
- `formatSize`;
- компонентов.

Самые быстрые полезные тесты:

1. reducer transitions;
2. validation cases;
3. render empty/result states;
4. upload file validation.

### 7. Ошибки сервиса слишком общие

Сейчас любой exception превращается в одно сообщение.

Для реального backend лучше различать:

- network error;
- 400 validation error;
- 413 payload too large;
- 415 unsupported media type;
- 500 server error.

### 8. Нет env-настройки API URL

Когда появится backend, frontend понадобится переменная:

```text
VITE_API_BASE_URL
```

Её можно добавить в `.env.example` и читать через:

```ts
import.meta.env.VITE_API_BASE_URL
```

### 9. Нужно уточнить production Docker

Текущий Dockerfile запускает dev server. Для финальной демонстрации лучше production build.

### 10. Нужно решить, как показывать реальные evidence

Сейчас есть:

- `sourceTitle`;
- `sourceReference`;
- `sourceExcerpt`.

Для настоящей проверки может понадобиться:

- `ruleId`;
- `ruleTitle`;
- `evidenceText`;
- `page`;
- `confidence`;
- `requiresManualReview`.
