# Фронтенд: полный разбор кода

## Назначение

Frontend — браузерная часть онлайн-деканата. Пользователь выбирает тип документа, прикрепляет файл и запускает проверку; вопрос необязателен. Интерфейс показывает распознанные поля, предварительную комплектность, текстовый ответ, действия по замечаниям и OCR-текст.

OCR, извлечение полей, проверка комплектности и классификация вопроса выполняются на backend. Решение о принятии документа остаётся за сотрудником деканата. Backend уже формирует готовый ответ для API и экспорта, но интерфейс пока использует свой шаблон по классификации, полям и валидации.

## Что пользователь видит сейчас

| Сценарий | Что происходит |
| --- | --- |
| Загрузил документ без вопроса | Кнопка «Проверить комплектность» отправляет стандартный вопрос «Содержит ли документ все обязательные сведения?» вместе с файлом |
| Ввёл вопрос | Кнопка «Задать вопрос» отправляет файл и вопрос; результат содержит и ответ, и комплектность |
| Найдены пропуски | Появляется блок «Что сделать перед подачей» с отдельной строкой для каждого пропуска |
| Нажал на замечание | Раскрывается подробное действие; ссылка рядом открывает пункт Положения |
| Исправил поле вручную | Старые ответ и рекомендации скрываются, появляется «Нужна повторная проверка», кнопка меняется на «Перепроверить документ» |
| Перепроверил документ | Backend пересчитывает результат с исправлениями, список действий строится заново |

Пример: выберите справку об обучении, загрузите `data/documents/open-002.pdf`, оставьте вопрос пустым и запустите проверку. В образце отсутствует дата выдачи: появится замечание «Дата выдачи», действие по нему и ссылка на пункт 3.1.

Рекомендации помогают сверить документ с оригиналом. Ввод значения в интерфейсе исправляет распознавание, но не заполняет бумажный документ. Список не показывается, если обязательных пропусков нет.

## Как читать этот разбор

Начните со сценариев выше, затем посмотрите поток запроса и карту файлов ниже. Для запуска используйте [README фронтенда](../../../frontend/README.md), для подробного API-потока — [README фичи](../../../frontend/src/features/document-check/README.md).

## Технологии и вход

- React 18 строит интерфейс из компонентов.
- TypeScript описывает модели UI и API.
- Vite запускает dev сервер и собирает приложение.
- SCSS хранит стили по разделам.
- Тесты запускаются встроенным Node test runner.

src/main.tsx подключает стили и рендерит App в элемент #root. В src/App.tsx путь /help показывает справочник, /rules — Положение, остальные пути открывают проверку. React Router не используется.

## Страница проверки

src/pages/DocumentCheckerPage.tsx собирает HeroSection, workflow проверки и footer. Основной сценарий находится в features/document-check/components/DocumentCheckWorkflow.tsx.

| Компонент | Назначение |
| --- | --- |
| DocumentUploadPanel | Выбор типа, зона загрузки, выбранный файл и ошибка |
| ExtractedFieldsPanel | Поля из ответа backend |
| CheckResultPanel | Комплектность, текст ответа, действия и источники |
| QuestionForm | Необязательный вопрос и запуск проверки |
| HelpPage | Статичная инструкция |

Компоненты загрузки лежат в components/upload/, строка поля - в components/fields/, а статус, ответ и источники - в components/result/. Workflow связывает состояние с презентационными компонентами; панели не вызывают API самостоятельно.

## Состояние формы

Модель состояния находится в features/document-check/types/documentCheck.ts. Она содержит выбранный файл, тип документа, вопрос, последний результат, признак обработки и ошибки.

Хук hooks/useDocumentCheck.ts связывает интерфейс с reducer и сервисом:

- addFile проверяет и принимает выбранный файл.
- removeFile удаляет файл и результат.
- setDocumentType и setQuestion обновляют ввод и очищают устаревший результат.
- runCheck валидирует форму, запускает запрос и сохраняет результат или ошибку.

model/validateDocument.ts проверяет формат JPEG, PNG или PDF по расширению и MIME, ненулевой размер до 10 МиБ, наличие файла и типа документа, длину вопроса до 2000 символов. Пустой вопрос и строка из пробелов допустимы. Backend независимо проверяет вход повторно.

model/documentCheckReducer.ts описывает переходы состояния. check/started очищает старый результат и включает обработку; check/succeeded сохраняет ответ; check/failed отображает ошибку. Изменение вопроса и типа сбрасывает предыдущий ответ.

Типы документов пока хранятся статически в data/documentTypes.ts: study_certificate, academic_leave_application и internship_certificate. useDocumentTypes читает список через интерфейс DocumentTypeCatalog.

## Выбор сервиса и API

Интерфейс DocumentCheckService задаёт метод analyze. services/documentCheckService.ts выбирает API сервис по умолчанию или демо сервис, если VITE_USE_DEMO_SERVICE=true. Демо режим показывает фиксированные примеры и не обрабатывает загруженный файл.

Настройки Vite читаются в src/shared/config/env.ts. Для локального backend файл frontend/.env.local обычно содержит:

~~~dotenv
VITE_USE_DEMO_SERVICE=false
VITE_OCR_API_URL=/ocr-api
~~~

vite.config.ts проксирует /ocr-api к http://127.0.0.1:8000 и убирает этот префикс перед запросом. Это работает в dev сервере. Production серверу нужен собственный reverse proxy или прямой API URL с настроенным CORS.

services/ApiDocumentCheckService.ts координирует отправку, чтение JSON, проверку ответа и преобразование для UI. services/api/analyzeDocument.ts отправляет POST /analyze как multipart/form-data:

| Поле | Назначение |
| --- | --- |
| photos | Один файл |
| prompt | Обязательная непустая строка: введённый вопрос или стандартный вопрос о комплектности |
| document_type | Код типа документа |
| manual_fields | Необязательный JSON-массив исправленных пользователем полей: id и value |

Content-Type не задаётся вручную: браузер добавляет multipart boundary. Ошибки FastAPI и сети преобразуются функцией services/api/readApiError.ts. Она обрабатывает, в частности, HTTP 413, 422, 503 и 504, а также строковый и массивный detail.

Поле формы необязательно для пользователя, но `prompt` обязателен для API. В services/api/analyzeDocument.ts константа COMPLETENESS_QUESTION содержит «Содержит ли документ все обязательные сведения?». Если question.trim() пуст, HTTP-клиент подставляет эту строку; иначе отправляет исходный вопрос без изменений. Само поле формы остаётся пустым. Backend классифицирует стандартный вопрос обычным способом: отдельной ветки обработки пустого prompt на backend нет.

Ручная корректировка доступна после первого результата для статусов review, missing и manual. Поле со статусом found пока редактировать нельзя. Reducer помечает непустое значение как manual; hooks/useDocumentCheck.ts выбирает такие поля и передаёт сервису. services/api/analyzeDocument.ts добавляет их в multipart как JSON в manual_fields. Backend пересчитывает проверку, mapper помечает применённые сервером исправления источником manual. Исходный файл не меняется.

После правки reducer переводит общий статус в unknown, очищает список действий и ставит `validation.needsRecheck = true`. CheckAnswer скрывает прежние ответ, сводку и рекомендации, показывает просьбу перепроверить документ. После нового успешного запроса mapper создаёт свежий результат без needsRecheck.

Подписи кнопки QuestionForm имеют приоритет: «Проверяем…» во время запроса → «Перепроверить документ» при наличии ручных полей или needsRecheck → «Задать вопрос» при непустом вопросе → «Проверить комплектность» при пустом.

Изменение вопроса, типа или файла очищает предыдущий результат вместе с правками. Даже повторный вопрос отправляет исходный файл и выполняет OCR заново. Кеширования анализа пока нет.

Текущая подсказка ExtractedFieldsPanel привязана к наличию полей manual и может остаться после успешной перепроверки. Для определения устаревшего результата ориентируйтесь на needsRecheck, а не только на эту подсказку.

## Проверка контракта и mapping

Ответ сначала считается неизвестным JSON. services/api/parseAnalyzeResponse.ts проверяет допустимый тип документа, значения полей, статусы комплектности, массивы пропусков и источников, а также классификацию вопроса. Для классификации field проверяется, что указанное поле есть в fields. Если форма ответа неверна, UI показывает ошибку о несовпадении версий backend.

Контракт описан в features/document-check/types/api.ts. Backend возвращает:

- document_type;
- fields со строками или boolean;
- необязательный ocr_text;
- validation со статусом document_ok или missing_fields, списком пропусков и источников;
- classification с intent field, validation, decision или unsupported.

Также backend возвращает готовые answer, answerable, value, sources и список применённых исправлений manual_fields. Frontend использует manual_fields для отметки источника ручных значений; остальные готовые поля ответа сейчас не входят в его DTO и не используются.

services/api/mapAnalyzeResponse.ts преобразует API DTO в модель DocumentCheckResult для интерфейса. Здесь создаются подписи и значения полей, статусы, сводка комплектности, ссылки на источники и текст OCR. Подписи находятся в data/fieldLabels.ts. Если ocr_text отсутствует, показывается текст-заглушка; остальные данные продолжают отображаться.

## Формирование ответа

model/buildDocumentAnswer.ts использует classification backend и выбирает шаблон:

- field показывает запрошенное значение или сообщает, что оно не найдено;
- boolean false для подписи или печати означает известное отсутствие;
- validation показывает пропущенные обязательные поля и напоминает о решении сотрудника деканата;
- decision объясняет, кто принимает окончательное решение;
- unsupported сообщает, что ответа нет.

Ответ на вопрос и комплектность независимы. Например, отсутствие подписи может быть известным ответом и одновременно обязательным пропуском. Статус берётся из validation, а текст ответа - из classification. Положительный статус не означает, что документ принят.

Фронтенд не интерпретирует произвольный текст Положения. Для перехода на уже готовый ответ backend нужно расширить types/api.ts, проверку структуры и mapper. Компоненты продолжат получать DocumentCheckResult.

## Список действий: от пропуска до строки в интерфейсе

Данные проходят так:

~~~text
backend: validation.missing_fields + validation.sources
  → mapAnalyzeResponse.ts
  → buildDocumentActions(document_type, validation)
  → result.validation.actions
  → CheckAnswer.tsx
  → DocumentActions.tsx
~~~

`buildDocumentActions.ts` не определяет, полон ли документ. Он получает уже найденные backend пропуски и превращает каждый уникальный ключ в действие. Если статус document_ok, возвращается пустой массив. Список появится и при вопросе о конкретном поле, если у документа есть другие обязательные пропуски.

Каждый элемент типа DocumentNextAction содержит:

| Свойство | Что хранит |
| --- | --- |
| fieldId | Ключ пропущенного поля, например issue_date |
| title | Русское название из data/fieldLabels.ts |
| description | Рекомендацию сверить оригинал, переснять его или дополнить сведения |
| sources | Ссылки на требования из validation.sources |

Для текстовых полей используется пункт 3.1, 4.1 или 5.1 по типу документа. Для подписи — 3.2, 4.2 или 5.2; для печати справок — 3.3 или 5.3. Ссылка добавляется только если соответствующий пункт присутствует в ответе backend. Заявление не получает требование печати.

Тексты учитывают, кто оформляет документ: заявление студент заполняет и подписывает сам; справку дополняет выдавший её вуз или организация. Рекомендации не обещают принятие документа и не проверяют подлинность отметок.

### Почему карточка теперь компактная

DocumentActions.tsx выводит нумерованный список. В строке видны название замечания, ссылка на правило и знак «+». Нажатие раскрывает полный текст через обычные HTML details/summary, без запроса к серверу; знак меняется на «−».

В styles/_results.scss классы `.document-actions` и `.document-action-list` задают отступы и оформление. Высота списка ограничена 230 px: при большом количестве замечаний или раскрытых текстов прокручивается сам список. Пустой список не занимает место.

При ручной правке массив actions очищается до повторной проверки. Свойства actions и needsRecheck существуют только в UI-модели, backend их не возвращает.

## Справка и общие части

src/pages/HelpPage.tsx собирает статическую справку из features/help/: заголовок, пример документа, шаги и советы. Тексты и пути к иллюстрациям находятся в features/help/data/. Backend справка не вызывает.

src/pages/RegulationPage.tsx показывает Положение из features/regulation/data/regulation.ts. RuleReferences.tsx превращает ссылки вида rule:3.1 в адрес /rules#rule-3-1. Текст здесь — копия учебного data/rules.md; изменения между этими файлами автоматически не синхронизируются. Ссылки field:<ключ> форматируются как подписи полей.

В src/shared/ находятся общие HeroSection, SiteFooter, Icon, PanelHeading, чтение переменных окружения и утилита форматирования размера файла.

## Тестирование и запуск

Команды выполняются из frontend/:

~~~bash
npm ci
npm test
npm run build
npm run dev
~~~

npm test запускает tests/*.test.mjs встроенным Node test runner. api-document-check.test.mjs проверяет API запрос, разбор ответа, классификации и ошибки. document-check-state.test.mjs проверяет ограничения и переходы состояния формы.

npm run build запускает tsc --noEmit и затем собирает сайт в dist/. Для настоящего OCR backend должен работать на 127.0.0.1:8000. Тесты frontend не запускают OCR или языковую модель и не измеряют качество распознавания.

На момент обновления документации в frontend 31 тест. Они включают подстановку стандартного вопроса для пустой строки и пробельного ввода, рекомендации для трёх типов и скрытие устаревших действий после правки. Тесты не проверяют внешний вид и высоту списка в браузере.

### Как проверить новые сценарии вручную

1. Запустите backend и frontend по README, откройте адрес из вывода Vite.
2. Проверьте open-002.pdf без вопроса: должны появиться пропуск даты выдачи и действие по нему со ссылкой 3.1.
3. Раскройте действие: полный текст должен появиться внутри строки. Откройте ссылку на Положение.
4. Проверьте документ с несколькими пропусками: у каждого будет отдельная строка; длинный список должен прокручиваться внутри блока.
5. Введите дату вручную: старые ответ и действия должны исчезнуть, статус станет «Недостаточно данных».
6. Нажмите «Перепроверить документ»: дата должна учитываться, её действие исчезнет из нового списка. Если есть другие пропуски, их действия останутся.
7. Введите вопрос «Кто принимает окончательное решение о принятии документа?» и отправьте его: должен появиться ответ о сотруднике деканата со ссылкой 1.3. Изменение вопроса сбрасывает прежний результат и правки.

Если backend отвечает `prompt: Field required`, проверьте актуальность frontend и Form Data запроса во вкладке Network: поле prompt должно присутствовать даже при пустом вводе. Обновлённый клиент отправляет стандартный вопрос, поэтому менять контракт backend не требуется. Если нет списка действий, проверьте, что включён API-режим и backend действительно вернул непустой missing_fields.
