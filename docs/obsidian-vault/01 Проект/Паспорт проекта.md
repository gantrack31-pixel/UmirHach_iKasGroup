# Паспорт проекта

## Задача

Собрать прототип цифрового помощника деканата: пользователь загружает студенческий документ, выбирает его тип, задаёт вопрос и получает распознанные сведения вместе с осторожным статусом проверки.

## Текущий MVP

1. Frontend принимает JPG, PNG и PDF до 10 МБ.
2. Пользователь вручную выбирает один из трёх типов:
   - справка об обучении;
   - заявление на академический отпуск;
   - справка о практике.
3. Frontend отправляет `multipart/form-data` в backend `/analyze`.
4. Backend запускает локальный EasyOCR, извлекает текст и поля.
5. Для подписи и печати используются простые визуальные эвристики.
6. Frontend отображает найденные поля, общий статус и OCR-ответ.
7. Страница `/help` показывает последовательность действий со скриншотами.

## Не входит в текущую версию

- Полноценная нормативная проверка по Положению.
- Генерация доказательного ответа с реальным `rule_id`.
- Экспорт `results.json` по официальной схеме.
- Автоопределение типа документа.
- Публичная эксплуатация с авторизацией, rate limit и политикой персональных данных.

## Ключевые решения

- OCR и извлечение выполняются локально; внешние OCR/LLM API не используются.
- Тип документа выбирается вручную, чтобы backend применял правильную схему полей.
- Backend не сохраняет файлы в постоянное хранилище.
- Логи backend не содержат вопрос, OCR-текст и содержимое файлов.
- Frontend по умолчанию использует `ApiDocumentCheckService`; demo-сервис включается только через `VITE_USE_DEMO_SERVICE=true`.

## Главные ограничения

- EasyOCR может плохо читать даты, кавычки, мелкий текст и сканы с перспективой.
- Подпись/печать проверяются эвристически и не доказывают подлинность.
- На CPU первый запуск тяжёлый: EasyOCR скачивает и загружает модели.
- Один backend-процесс выполняет OCR по одному запросу за раз.

## Следующий целевой этап

Сделать не только распознавание, но и проверку: связать поля с правилами Положения, добавить безопасный ответ на вопрос, вернуть проверяемые основания и подготовить экспорт результата.
