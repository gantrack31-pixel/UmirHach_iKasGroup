# Совместная работа

Репозиторий содержит frontend и backend обычными файлами. Изменения обоих
сервисов публикуются в `gantrack31-pixel/UmirHach_iKasGroup`. Backend находится
в `backend/online-dekanat-backend`; вложенный Git-репозиторий не создавайте.

## Начало работы

1. Откройте корень проекта — папку с `docker-compose.yml`.
2. Проверьте `git status`: незакоммиченные изменения принадлежат текущей рабочей
   папке и могут мешать переключению ветки.
3. Обновите чистый `main` и создайте ветку под свою задачу:

```bash
git switch main
git pull --ff-only
git switch -c feature/my-change
```

Если Git сообщает, что изменения будут перезаписаны, сначала сохраните их
отдельным коммитом или stash. Не применяйте `reset --hard` или `clean` для
устранения этой ошибки. После слияния PR старые правки из stash не нужно
повторно применять целиком: сначала сравните их с актуальным `main`.

## Запуск

- [Первый запуск](README.md#первый-запуск-docker) — Docker, без зависимостей на хосте.
- [DOCKER.md](DOCKER.md) — модели, порты, логи, экспорт и остановка.
- [Backend](backend/online-dekanat-backend/README.md) и
  [frontend](frontend/README.md) — запуск для локальной разработки.

Docker использует собранные файлы. После правки кода выполните из корня проекта
`docker compose up -d --build --wait`. Для автоматического обновления frontend
используйте локальный Vite; он ожидает backend на `127.0.0.1:8000`.

## Проверки перед PR

Frontend, из `frontend/` с Node.js 24:

```bash
npm ci
npm test
npm run build
```

Backend, из `backend/online-dekanat-backend/` с активным `.venv` и Python 3.12+:

```bash
python -m pip install -r requirements-test.txt
python -m pytest
python -m ruff check .
python -m ruff format --check .
```

Для этих unit-тестов backend не нужны Tesseract и веса моделей. Если backend
уже установлен для запуска, используйте то же окружение. После изменения
OCR дополнительно проверьте реальные документы: подмена OCR в unit-тестах
не измеряет качество распознавания. Docker-проверки описаны в DOCKER.md.

В описании PR укажите поведение до и после изменения, выполненные проверки
и ограничения. При изменении запуска обновляйте README соответствующего
сервиса и DOCKER.md. Контракт API согласуйте между backend, DTO и parser frontend.

## Границы задач

- Backend/API: OCR, поля, правила комплектности, классификация, ответы и экспорт.
- Frontend: загрузка, поля, ручные исправления, результат и рекомендации.
- Данные и защита: учебный набор, метрики, сценарии демонстрации.

`data/README.md` и `data/rules.md` содержат требования кейса: не меняйте сами
требования ради прохождения проверки. Эталоны не подставляются вместо обработки.
Не коммитьте `.venv`, `node_modules`, модели, секреты и пользовательские загрузки.
Не редактируйте одну общую заметку Obsidian одновременно без согласования.
