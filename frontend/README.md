# StudDoc: Frontend

Интерфейс проверки студенческих документов на React 18, TypeScript и Vite 5.
Студент выбирает тип документа, загружает файл и при желании задаёт вопрос. Интерфейс
показывает поля, предварительную проверку комплектности, ответ и OCR-текст.
При пустом поле кнопка «Проверить комплектность» отправляет стандартный вопрос
«Содержит ли документ все обязательные сведения?»;
с вопросом кнопка «Задать вопрос» запускает анализ с ответом.

## Как пользоваться

1. Выберите тип документа и загрузите файл.
2. Оставьте вопрос пустым и нажмите «Проверить комплектность» либо введите вопрос
   и нажмите «Задать вопрос». Строка из пробелов тоже считается пустым вопросом.
3. Посмотрите найденные поля, статус и ответ. При пропусках под результатом
   появится список «Что сделать перед подачей».
4. Нажмите на замечание, чтобы раскрыть рекомендацию. Ссылка рядом с названием
   открывает соответствующий пункт Положения на `/rules`.
5. Если OCR не прочитал заполненное поле, уточните значение в карточке полей
   и нажмите «Перепроверить документ». Пока повторная проверка не выполнена,
   старые ответ и список действий скрыты, статус — «Недостаточно данных».

Список действий учитывает тип документа: например, для заявления нужна подпись
студента, а для справки о практике — подпись руководителя и печать организации.
Если все обязательные сведения найдены, список не показывается.

Изменение вопроса, типа документа или файла сбрасывает предыдущий результат,
включая ручные правки. Каждый новый запрос повторно отправляет исходный файл
на backend; повторные вопросы пока не используют кеш OCR.

## Требования

- Для разработки и тестов рекомендуется Node.js 24 и npm.
- `npm test` использует встроенный тестовый раннер Node и `--experimental-strip-types`;
  Node.js 20 из текущего Dockerfile эту команду не поддерживает.
- Для обработки настоящих файлов нужен запущенный backend на `127.0.0.1:8000`.
  Установка OCR и локальной модели описана в [README backend](../backend/online-dekanat-backend/README.md).

## Быстрый запуск

Команды из корня репозитория `Code`:

```bash
cd frontend
npm ci
npm run dev
```

Откройте адрес из вывода Vite, обычно `http://localhost:5173`.
Если порт занят, Vite предложит другой. Страница `/` содержит проверку документа,
`/help` — справочник, `/rules` — текст учебного Положения со ссылками на пункты.
Навигация использует обычные ссылки.

## Команды

| Команда | Назначение |
| --- | --- |
| `npm run dev` | Сервер разработки с прокси к backend |
| `npm test` | Проверки API-адаптера, валидации формы и состояния |
| `npm run build` | Проверка TypeScript и сборка в `dist/` |
| `npm run preview` | Локальный просмотр готовой сборки |

Тесты подставляют ответы API и не запускают Tesseract или Qwen.
Они не измеряют качество распознавания и классификации настоящих вопросов.

## Настройки

При необходимости создайте `frontend/.env.local` по примеру `frontend/.env.example`:

```dotenv
VITE_USE_DEMO_SERVICE=false
VITE_OCR_API_URL=/ocr-api
```

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `VITE_OCR_API_URL` | `/ocr-api` | Базовый URL API; адаптер добавляет `/analyze` |
| `VITE_USE_DEMO_SERVICE` | API-режим | Только строка `true` включает статические демо-сценарии |

Vite читает переменные при запуске или сборке. После изменения `.env.local`
перезапустите dev-сервер. Чтение настроек собрано в `src/shared/config/env.ts`.
Переменные с префиксом `VITE_` доступны браузеру; секреты в них хранить нельзя.
Корневой `.env.example` с `VITE_API_BASE_URL` относится к старому каркасу:
эта переменная текущим фронтендом не используется.

В dev-режиме `vite.config.ts` переводит `/ocr-api/analyze` в
`http://127.0.0.1:8000/analyze`. Прокси настроен для `npm run dev`,
а не для production-сервера или `npm run preview`. При размещении сборки
нужно настроить такой же reverse proxy либо прямой URL API и CORS на backend.
Статические ссылки `/assets/...` также требуют раздачи соответствующей папки
`assets/`, включая изображения справочника.

  features/

      data/                        подписи, типы, статусы и демо-сценарии
      hooks/                       связь React с состоянием и сервисами
      model/                       reducer, валидация, ответ и рекомендации
      services/

Порядок подключения стилей задаётся `src/styles.scss`.

## Контракт API

`POST /analyze` принимает `multipart/form-data`. Заголовок `Content-Type`
формируется браузером вместе с multipart boundary.

| Поле | Значение |
| --- | --- |
| `photos` | Один `File`: JPEG, PNG или одностраничный PDF, до 10 МиБ |
| `prompt` | Обязательная непустая строка до 2000 символов: введённый вопрос или стандартный вопрос о комплектности |
| `document_type` | `study_certificate`, `academic_leave_application` или `internship_certificate` |
| `manual_fields` | Необязательный JSON-массив исправлений `[{"id":"issue_date","value":"2026-10-15"}]` |

Поле вопроса необязательно только для пользователя. `analyzeDocument.ts` всегда
отправляет `prompt`: если `question.trim()` пуст, подставляет константу
`COMPLETENESS_QUESTION` со значением «Содержит ли документ все обязательные
сведения?». Введённый вопрос отправляется без изменений. Подстановка не меняет
текст в поле формы. Backend сохраняет обычный контракт с обязательным вопросом
и классифицирует его стандартным способом. Ручные исправления передаются вместе
с ним как прежде.

Ошибка `prompt: Field required` означает, что клиент не отправил обязательный
параметр: проверьте актуальность frontend и поле `prompt` в Form Data запроса
`/analyze` через вкладку Network инструментов разработчика.

Ответ содержит `document_type`, `fields`, `ocr_text`, `validation` и
`classification`. `ocr_text` допускается пропустить; остальные части
проверяются перед преобразованием в модель интерфейса.

- `validation.status`: `document_ok` или `missing_fields`.
- `validation.missing_fields`: ключи недостающих полей.
- `validation.sources`: ссылки вида `rule:3.1`.
- `classification.intent`: `field`, `validation`, `decision` или `unsupported`.
- Для `field` значение `classification.field` должно быть ключом из `fields`;
  для остальных намерений оно равно `null`.

Backend также возвращает `answer`, `answerable`, `value`, `sources` и
`manual_fields` — список применённых исправлений. Текущий frontend формирует
собственный текст ответа из `classification`, `fields` и `validation`;
готовые поля ответа backend он не использует. `manual_fields` нужен mapper,
чтобы отметить подтверждённые сервером значения источником `manual`.

Список действий создаётся на frontend из `validation.missing_fields`.
Его элементы не являются новыми требованиями и не передаются в API.

## Где менять поведение

Все пути ниже указаны относительно `src/`.

| Что изменить | Файл |
| --- | --- |
| Названия кнопок и подсказку про необязательный вопрос | `features/document-check/components/QuestionForm.tsx` |
| Отправку вопроса и ручных правок | `features/document-check/services/api/analyzeDocument.ts` |
| Тексты рекомендаций и соответствие типам документов | `features/document-check/model/buildDocumentActions.ts` |
| Раскрытие пунктов списка | `features/document-check/components/result/DocumentActions.tsx` |
| Отступы, размеры строк и прокрутку списка | `styles/_results.scss`, классы `.document-actions` и `.document-action-list` |
| Поведение после ручной правки | `features/document-check/model/documentCheckReducer.ts` и `components/result/CheckAnswer.tsx` внутри той же фичи |
| Подписи извлечённых полей | `features/document-check/data/fieldLabels.ts` |
| Текст Положения и адреса пунктов | `features/regulation/data/regulation.ts` |

В компактном списке видны название замечания и ссылка. Полный текст действия
раскрывается через HTML `details/summary`; высота списка ограничена 230 px,
при переполнении появляется внутренняя прокрутка.

Фронт отображает ошибки `413`, `422`, `503` и `504`, включая строковый и
массивный `detail` FastAPI. Некорректный успешный JSON получает отдельное
сообщение о несовпадении контракта.

## Границы реализации

OCR, извлечение полей, комплектность и классификация вопроса выполняются
на backend. Фронт формирует шаблонный ответ по уже полученной классификации.
Положительный статус комплектности не означает принятие документа.
Отсутствующая подпись может быть одновременно пропуском при проверке
комплектности и известным ответом на вопрос о её наличии.

Фронт не запускает нейросеть и не читает `data/rules.md` во время работы.
Для страницы `/rules` используется копия текста в `features/regulation/data/regulation.ts`.
При изменении учебного Положения эту копию, тексты рекомендаций и backend-правила
нужно согласовать вручную. Произвольные ответы по всему тексту не реализованы.
Экспорт итогового `results.json` доступен через CLI backend; кнопки экспорта
в интерфейсе нет. Команда приведена в [README backend](../backend/online-dekanat-backend/README.md).
Демо-режим показывает фиксированные примеры без обработки загруженного файла.
Эти примеры не содержат полноценной валидации и списка действий.
