# Проверка документов

Фича объединяет загрузку файла, необязательный вопрос студента, карточку полей,
предварительную проверку комплектности, список действий и блок источников. Страница
`pages/DocumentCheckerPage.tsx` размещает её рядом с hero и footer;
внутренний сценарий собирает `components/DocumentCheckWorkflow.tsx`.

## Как запустить и проверить эту фичу

Первый запуск всего проекта: [DOCKER.md](../../../../DOCKER.md).
Команды Compose выполняются из корня проекта, а не из этой папки.
Локальная разработка: [README frontend](../../../README.md) и
[README backend](../../../../backend/online-dekanat-backend/README.md).
Без backend или в демо-режиме настоящий документ не распознаётся.

Для проверки загрузите `data/documents/open-002.pdf` как справку об обучении,
оставьте вопрос пустым и запустите проверку. Должны появиться пропуск даты
выдачи и действие со ссылкой на 3.1. В API всегда отправляется непустой prompt.

## Поток данных

1. `DocumentUploadPanel` и `QuestionForm` передают действия в `useDocumentCheck`.
2. `model/validateDocument.ts` проверяет файл, тип документа и длину вопроса.
   Пустой вопрос допустим.
3. `DocumentCheckService.analyze` получает оригинальный браузерный `File`,
   выбранный тип, вопрос и callback прогресса.
4. `ApiDocumentCheckService` вызывает HTTP-клиент, проверяет JSON и получает
   готовый `DocumentCheckResult` из mapper.
5. Mapper вызывает `buildDocumentAnswer` для ответа и `buildDocumentActions`
   для рекомендаций по пропускам.
6. Reducer сохраняет результат; панели отображают его без обращения к API.

## API и представление

Под результатом проверки выводится список «Что сделать перед подачей».
`model/buildDocumentActions.ts` формирует его по `validation.missing_fields`:
советы сверить текст с оригиналом, уточнить подпись или печать для выбранного
типа документа. Ссылки на требования берутся из источников проверки.
После ручной правки старые рекомендации скрываются до повторного анализа.

Запрос: `POST /analyze`, поля multipart `photos`, `prompt`, `document_type`.
Ограничения: один JPEG/PNG/одностраничный PDF до 10 МиБ, вопрос до 2000 символов.
В интерфейсе вопрос необязателен, но API всегда получает непустой `prompt`.
Если пользователь ничего не ввёл, frontend подставляет стандартный вопрос
«Содержит ли документ все обязательные сведения?». Backend обрабатывает его
через обычный классификатор. Ручные исправления передаются в том же запросе.
Структура ответа:

```ts
type OcrAnalyzeResponse = {
  document_type: DocumentType;
  ocr_text?: string;
  fields: Record<string, string | boolean>;
  validation: {
    status: "document_ok" | "missing_fields";
    missing_fields: string[];
    sources: string[];
  };
  classification:
    | { intent: "field"; field: string }
    | { intent: "validation" | "decision" | "unsupported"; field: null };
};
```

Комплектность и возможность ответить на вопрос независимы:

- Статус панели определяется `validation.status` от backend.
- Намерение `field` показывает значение одного поля или сообщает, что его нет.
- Boolean `false` означает известное отсутствие подписи/печати. Это ответ
  на вопрос о наличии, хотя комплектность документа может быть неполной.
- `validation` перечисляет пропуски и использует источники из backend.
- `decision` показывает шаблонный ответ о сотруднике деканата с `rule:1.3`.
- `unsupported` показывает отсутствие ответа без вымышленных источников.

`answerSources` сохраняет машинные ссылки `field:<key>` и `rule:<number>`.
Mapper формирует читаемые подписи для блока источников; OCR-текст остаётся
отдельным `sourceExcerpt`. Отсутствие `ocr_text` не приводит к падению.

Это форматирование результата, а не генерация ответа нейросетью.
Backend уже возвращает готовые `answer`/`answerable`/`value`/`sources`,
но текущий UI строит свой шаблонный ответ и не проверяет эти дополнительные поля.
DTO выше описывает используемую frontend часть ответа; в `types/api.ts` также
есть необязательный `manual_fields?: string[]` — список применённых исправлений.
Фронт не интерпретирует произвольный текст Положения.

## Проверка с вопросом и без него

`QuestionForm` отправляет одну и ту же форму по кнопке или Enter.
Подпись кнопки определяется в таком порядке:

| Условие | Подпись |
| --- | --- |
| Запрос выполняется | «Проверяем…» |
| Есть ручные значения или `validation.needsRecheck` | «Перепроверить документ» |
| Вопрос содержит непробельные символы | «Задать вопрос» |
| Вопрос пустой или из пробелов | «Проверить комплектность» |

Входной `question` остаётся строкой. В `analyzeDocument.ts` хранится константа
`COMPLETENESS_QUESTION = "Содержит ли документ все обязательные сведения?"`.
Сервис всегда добавляет `prompt` в multipart: если `question.trim()` пуст,
использует константу; иначе передаёт исходный вопрос без изменения пробелов.
Подстановка выполняется только при отправке и не заполняет поле формы.
Backend не получает пустой вопрос и не нуждается в специальном режиме проверки.
Ограничение 2000 символов сохраняется и на frontend, и на backend.

## Как строится список действий

`buildDocumentActions(documentType, validation)` получает результат backend.
Для `document_ok` возвращает пустой массив. Для `missing_fields` создаёт по
одному элементу на уникальный ключ пропуска. Проверку комплектности повторно
не вычисляет; наличие списка не зависит от намерения вопроса.

| Часть `DocumentNextAction` | Смысл |
| --- | --- |
| `fieldId` | Ключ пропуска из `validation.missing_fields` |
| `title` | Подпись поля из `getFieldLabel` |
| `description` | Что сверить в оригинале и что сделать, если сведения отсутствуют |
| `sources` | Соответствующие требованию ссылки, присутствующие в `validation.sources` |

Тексты хранятся в `model/buildDocumentActions.ts`. Для текстового поля рекомендация
предлагает сверить оригинал: переснять заполненное поле или дополнить документ.
Для заявления пользователь может заполнить поле сам; для справки предлагается
обратиться в выдавший её вуз или организацию.

Подпись и печать учитывают выбранный тип:

| Тип | Текстовые поля | Подпись | Печать |
| --- | --- | --- | --- |
| Справка об обучении | `rule:3.1` | Сотрудник вуза, `rule:3.2` | Вуз, `rule:3.3` |
| Заявление на академический отпуск | `rule:4.1` | Студент, `rule:4.2` | Не требуется |
| Справка о практике | `rule:5.1` | Руководитель практики, `rule:5.2` | Организация, `rule:5.3` |

Ссылки фильтруются по источникам backend: если ожидаемого пункта там нет,
элемент остаётся без ссылки. Правила для новых типов нужно добавлять и на backend,
и в этот словарь; функция не читает `data/rules.md` автоматически.

Mapper сохраняет массив в `result.validation.actions`. `CheckAnswer` передаёт
его в `DocumentActions`. В каждой строке видны название и `RuleReferences`;
`details/summary` раскрывает полный текст. Пустой список не рендерится.
В `_results.scss` высота `.document-action-list` ограничена 230 px,
длинный список прокручивается внутри блока. Раскрытие не вызывает API.

## Ручные правки и повторная проверка

1. `ExtractedFieldRow` разрешает менять поля со статусом `missing`, `review`
   или `manual`. Поля `found` сейчас не редактируются.
2. `field/manualChanged` обновляет значение. Непустое получает статус и источник
   `manual`; пустое — статус `missing`.
3. Reducer ставит общему статусу `unknown`, очищает `validation.actions`
   и устанавливает `validation.needsRecheck = true`.
4. `CheckAnswer` вместо прежнего ответа, сводки и действий показывает просьбу
   перепроверить документ. `DocumentCheckWorkflow` меняет подпись кнопки.
5. `useDocumentCheck.runCheck` собирает непустые поля со статусом `manual`,
   а `analyzeDocument` отправляет их как JSON в `manual_fields` вместе с файлом.
6. Backend применяет исправления до валидации. Новый mapper заново строит
   рекомендации и отмечает серверные `manual_fields` источником `manual`.
   Новый результат не имеет `needsRecheck`.

`actions` и `needsRecheck` — свойства модели UI, в контракт backend они не входят.
Ручная правка не меняет изображение и не добавляет подпись или дату в оригинал.
Для демо-примеров без `validation` этот механизм рекомендаций не применяется.

Изменение вопроса, типа или файла сбрасывает весь результат вместе с правками.
Каждый анализ заново загружает файл и выполняет OCR; сессии вопросов и кеша нет.
Подсказка в `ExtractedFieldsPanel` сейчас зависит от наличия поля `manual`,
поэтому может оставаться и после успешной перепроверки. Признак действительно
устаревшего результата в API-режиме — `validation.needsRecheck`.

## Тестирование

Из папки `frontend`:

```bash
npm test
npm run build
```

`tests/api-document-check.test.mjs` проверяет публичный API-адаптер:
все четыре намерения, пропущенные значения, boolean-флаги, источники,
некорректный JSON, ошибки API, состав multipart-запроса, подстановку стандартного вопроса
для пустой строки, пробелов и табуляции с переносом строки, а также рекомендации для трёх типов документов.
`tests/document-check-state.test.mjs` фиксирует лимиты формы и переходы
состояния при выборе файла, изменении вопроса, успехе и ошибке запроса,
а также сброс действий после ручного исправления.

Тесты выполняются встроенным раннером Node. Импорты исполняемых TypeScript-модулей
в тестируемом графе имеют расширение `.ts`, чтобы Node мог разрешить их без
Vite; это разрешено текущим `tsconfig.json`. Дополнительный тестовый framework
или сборка тестов не нужны. Настоящие OCR и веса модели здесь не используются.

## Дальнейшее развитие

Чтобы перейти на готовый текст ответа backend, нужно расширить
`types/api.ts`, проверку контракта и mapper. JSX-компоненты должны продолжать
получать `DocumentCheckResult`. Добавление новых полей затрагивает их подписи
в `data/fieldLabels.ts`, а не HTTP-клиент или компоненты.

Настройки окружения и запуск описаны в [README фронтенда](../../../README.md).
